# Engineering decisions

1. **One Spring Boot application and PostgreSQL.** All accounting can commit atomically without distributed transactions. Microservices, Kafka, AI and blockchain do not solve a Phase 1 requirement.
2. **Java 21, Spring Boot 3.5, Maven.** Use a compatible stable 3.x line and pinned dependency versions. A full JDK is required, not just a JRE. The Boot BOM manages Spring/Hibernate/Testcontainers compatibility.
3. **Session cookies over browser-held bearer tokens.** HttpOnly authentication cookies reduce script access to credentials. SameSite and CSRF checks protect cookie-based writes. Explicit session persistence and ID rotation are needed because login uses a JSON controller rather than Spring's form-login filter. Sessions are intentionally single-process for now.
4. **USD decimal strings end to end.** `BigDecimal` and PostgreSQL numeric provide exact accounting; string DTO serialization preserves precision through JSON. Display-only browser formatting may use `Number`. No implicit USD/SAR conversion.
5. **Pessimistic portfolio lock.** A modest educational workload favors clear serialization over optimistic retry complexity. Lock before idempotency lookup so concurrent duplicates see committed state. The database unique key remains a backstop. Never hold this lock during external market-data I/O.
6. **FIFO remaining-cost allocation.** Preserve settled cents, including final remainders. Retain allocation records for explaining sell P/L; an average purchase price alone loses the evidence.
7. **Append-only financial history plus cached balance.** Cached cash makes authorization-time checks straightforward; ledger records permit reconciliation. PostgreSQL triggers protect history from accidental DML. Stronger DB role separation, tamper evidence and automated reconciliation are future operational work.
8. **JPA for aggregates; JDBC for focused queries/history.** Avoid modeling large immutable histories as mutable entity graphs. Both use the same DataSource/transaction manager. This is a practical persistence boundary, not a commitment to replace the database behind every interface.
9. **Explicit historical simulation.** A date and fictional close are shown at execution; later-dated orders cannot be followed by backdated orders. Two clocks distinguish modeled execution from actual recording. No fake live ticks.
10. **PostgreSQL tests, not H2 substitutes.** Locks, numeric semantics, partial indexes and immutability triggers must be exercised on the production database family. Testcontainers is required for backend verification and is not silently skipped when Docker is unavailable.
11. **Meaningful UI before charts.** Phase 1 presents records, cash and positions with explicit empty/failure states. Performance/risk charts require Phase 2/3 data contracts; decorative fabricated analytics would undermine trust. Dark theme only initially; light theme is optional later refinement.
12. **Local-first security boundary.** Random ignored local DB credentials, loopback port binding, nonroot app containers, authenticated OpenAPI JSON, no permissive CORS. This is not a public production deployment; see ARCHITECTURE.md for remaining controls.

13. **Fixed persisted historical funding baseline.** All existing/new portfolios receive opening capital on 2022-01-03. Real audit clocks remain intact. This avoids inferred dates shifting when the first trade changes and gives no-trade portfolios a stable baseline. It is explicitly a simulation convention, not backdated real account activity.
14. **Immutable reconstruction, not current lots.** Use buy/sell quantity and gross with recorded FIFO sell allocations to reconstruct each EOD. This preserves original rounding and excludes future sales from past holdings. No separate event-sourced write architecture or duplicate snapshots are necessary.
15. **Simple one-deposit returns.** Since-start P/L divides by initial funding; range change divides by starting EOD wealth. Deposits are never gains. TWR/MWR and annualization would add assumptions not justified by the current single-funding model.
16. **Exact-date marks and honest gaps.** Weekends/holes stay null while an asset is held. The equity chart breaks at those dates and the API names missing symbols. A cash-only/fully sold portfolio needs no closing prices. Zero denominators are undefined, not silently zero.
17. **One consistent bounded dashboard response.** Bulk-read under REPEATABLE READ and cap dates/orders/assets. The response includes all panels and compact daily points, avoiding request-per-date queries and inconsistent panel reads. Scale with evidence before introducing valuation caching/materialization.
18. **Accessible charts without client accounting.** Recharts handles SVG interaction only; decimal financial results come from Java. Keep the capital baseline, complete/gap counts, readable tooltips, keyboard controls, dated data table and allocation value list visible. Risk metrics remain Phase 3.


## Phase 3: separate exposure shocks from actual historical drawdown

Reuse Phase 2 immutable historical valuation rather than change trading or accounting. Historical shocks use fixed selected-date rounded exposures; actual drawdown uses the portfolio's changing historical holdings. Strict weekday alignment prevents multi-day gaps becoming daily returns; incomplete weekday windows make estimates unavailable. Cash-only zero risk is analytical, not fabricated history. Historical VaR uses nearest rank, with 100/500 minimums, rather than interpolation or a Gaussian fit. Exposure concentration is disclosed as Σ risky equity weights², not variance attribution. Stress reprices quantities to cents, returns signed contributions and never writes financial records. No schema, cache, external prices or additional infrastructure are needed. See PHASE3_RISK_SPEC.md for formulas/limits and PHASE3_SECURITY.md for dependency checks; a major framework migration is outside this phase.


## Phase 4: supported upgrade, durable intent and existing-stack operations

Adopt Boot 4 / Framework 7 only after a disposable prototype passed every original backend test; do not mix unsupported major versions. Compare scanner severity with official application preconditions, preserve historical findings, then resolve them with the available open-source patched framework. Scan test dependencies too; compatible Jackson/Tomcat maintenance fixes keep supported lines aligned.

Use PostgreSQL for expiring authentication attempt windows because it is already transactional and persists across process restarts. Avoid permanent account lockouts and arbitrary forwarded-header trust; disclose shared-client/distributed-abuse limits. Use Actuator/Micrometer, two explicit security chains and safe low-cardinality telemetry instead of introducing a monitoring service.

An ambiguous client request is a recoverable intent, not permission to create a new order. Persist its original key/payload before POST, freeze edits and check the owner-scoped stored result after refresh/login. Keep immutable PostgreSQL executions and portfolio locks as the authority. Record transaction telemetry after completion so rollback and business rejection do not look like committed trades.

Provide an explicit migration-only process and optional least-privilege serving profile without altering existing owner credentials or deleting local state. Exercise real scripts/grants and restore only new disposable databases, with fingerprint comparisons. Digest-pin/harden runtime images; record scan findings rather than equating a scan to security certification. Measure serial requests before optimizing: the observed workloads provide no case for caches, queues or an engine rewrite. No production-readiness claim; Phase 5 remains unstarted.

## Phase 5 — one-host release gates before presentation

Use one API and existing PostgreSQL/React infrastructure. A distinct HTTPS/private-network deployment prevents owner credentials and unsafe migration settings from leaking into the serving process. Membership/SET ROLE, ownership and effective PUBLIC-derived rights are checked, rather than assuming direct ACL revocation makes an existing role safe. PostgreSQL 17 provisioning failures use ON_ERROR_STOP instead of an unreliable quit exit argument.

Prefer the supported Alpine JRE publisher to carrying unused Ubuntu pebble. Remove only PostgreSQL gosu, whose root branch is eliminated by enforced non-root initialization; do not download a replacement privileged binary. Scan actual final images with visible Medium findings, immutable OCI checksums/source identity and a 48-hour DB freshness gate. Unknown scanner/network state is not a pass.

Use a local CA to prove TLS rather than bypass certificate checks. Preserve account budgets while separating edge client identities. Enrollment is closed by default; local testing opens an explicit window. Preserve one-JVM session semantics and reauthentication; shared sessions/HA add no requirement for this scope. Backup schedules/templates do not establish off-host recovery: missing real destination, host and operator inputs remain release blockers. Accessibility fixes are limited to keyboard-reachable scroll regions; visual identity and financial engines are retained.
